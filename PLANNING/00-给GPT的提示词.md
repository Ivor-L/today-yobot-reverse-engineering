# 背景

我要把一条叫「数字分身」的产品线做进我现有的桌面产品 YoBot 里。手里有四份材料，它们的可信度不同，请你分别对待。

## A. YoBot（要改造的对象）

微信私域运营 + AI Agent 桌面客户端。**Electron 外壳 + Vue 3 静态 SPA + 独立 Node 服务子进程**；macOS 侧挂原生 Helper 驱动 Python 编写的微信 RPA 插件。

- **核心资产**：微信界面自动化（RPA）、97 个 HTTP 接口（群发/自动加好友/朋友圈/通讯录同步/客户管理/自动 SOP/语音）、已对外暴露 7 个 MCP 工具（5 个只读）、License 商业化闭环、**多品牌白标**
- **已有一套相当完整的 Agent 内核**：`agent/` 145 模块、`memory/` 14 模块、`skills/` 72 模块、`knowledge/`、`scheduler/`、`channels/`、`gateway/`、完整插件系统 —— 详见 `PLANNING/02-YoBot资产清单.md`
- **关键性质**：以上全部来自**静态逆向分析**。恢复出的代码**从未真实启动运行过**，「接口存在」≠「功能可用」

## B. 数字分身（要新增的产品线）

把日常沟通变成**可追溯的记忆、可处理的事项、可复用的知识**，逐步形成由本人确认和控制的数字分身。六页面 + 九维 Wiki + 三个闭环。完整规格见 `DIGITAL-TWIN/product_plan.md` 与 `PLANNING/03-数字分身产品规格.md`。

**已有一份可交互原型**（`DIGITAL-TWIN/digital_twin_prototype.html`），带完整视觉规范。

## C. 数据现实（**最重要，请优先看**）

`PLANNING/01-数据现实与P0门槛.md`。这是本机实测结论，不是文档转述：

> **本机当前没有任何一条落盘的微信聊天消息。**
> 采集链路只通了一半：微信在线 ✅ → 界面自动化可用 ✅（RPA 真的读到了群消息）→ **消息不落盘 ❌** → **通讯录同步循环失败 ❌**。
> 通讯录同步 18 条失败里，**14 条是 `the single row click did not expose a verified focused remark field`** —— 微信的 Accessibility 元素结构变了，RPA 的选择器失效。

**产品方案（材料 B）的起点写的是「已有本地机器人能够取得微信历史与每日聊天记录」。这句话不成立。**

## D. Today（形态参照，不是技术路线）

另一个 AI 原生桌面助手。**不要照搬它的技术栈**，要抄的是它已验证的产品形态与工程范式：任务一等公民、引用式上下文、主动动作 + timing 反馈、记忆资产化、生成式契约、设计 token 层。详见 `PLANNING/04-Today范式与设计对标.md`。

# 我已经定了的三件事（不要重复问我）

1. **数字分身的六页功能是加进 YoBot 的**，不是另起一个独立产品。YoBot 现有的销售功能保留。
2. **合规暂不拍板，先做验证。** 数据层要设计成**可替换的适配器接口**，隔离对逆向组件的依赖；首版交付物不含逆向组件。
3. **第一阶段先攻数据打通。** 没有真实消息，六页面全是空壳。

# 我在另一份文档里已经做出的判断（请正面回应，同意或反对）

写在 `PLANNING/05-结合方案与决策地图.md` §一与§六，摘要：

> **数字分身 = 把 YoBot 的业务层从「销售专用」重构为「场景可配置」。** YoBot 现有 10 个页面全是销售动作，业务层是硬编码成「商品销售」单一场景的。数字分身要的不是"加六个页面"，而是这层通用化。

以及：

> **不要重写引擎。** `agent/` / `memory/` / `scheduler/` / `channels/` 都可以直接用（记忆层的召回阈值是用 45 组真实样本校准过的，注释里还记着上一版阈值「不可达」）。预算应该花在数据打通、业务层重构与前端上。

**如果你不同意这两条，请直接说，并给出证据。**
