> **性质声明**：本规格是产品侧设计，**不含任何上游已提供的能力承诺**。所有数据依赖见 `01-数据现实与P0门槛.md`。

## 一、产品定位与它带来的定位张力

一句话（`product_plan.md` §1）：

> 把日常沟通变成**可追溯的记忆、可处理的事项、可复用的知识**，并逐步形成由本人确认和控制的数字分身。

### 1.1 必须先解决的定位张力

产品方案 §1 明确写着：

> 产品不应只是聊天摘要器，也**不是把所有联系人当成客户的销售后台**

但 YoBot **就是**销售后台（客户管理 / 朋友圈 / 自动 SOP / 群发 / 加好友）。所以「在 YoBot 里加一个数字分身」在定位层是自相矛盾的。

**解法已经写在同一份方案里**（§1.3「通用化方式」）：

> 统一底层对象和处理流程，把不同场景的字段、阶段与优先规则**放入配置**。

方案给了五个场景，每个有各自的重点字段与**不宜混用的标准**：

| 场景 | 重点字段 | 不宜混用的标准 |
|---|---|---|
| 商品销售 | 规格、数量、预算、采购角色、交付条件、采购时间 | 购买某商品不代表对另一商品有高意向 |
| 项目／服务 | 目标、范围、现有流程、参与角色、预算、排期、验收 | 不能凭泛泛咨询认定可成交 |
| 合作共创 | 共同目标、分工、双方投入、资源许可、时间与下一步 | 不以采购预算作唯一判断依据 |
| 内部协作 | 负责人、依赖、交付物、阻碍、期限 | **不给同事设置销售意向等级** |
| 个人事务 | 约定、待回复、共同事项、提醒边界 | **不把朋友统一纳入商业评分** |

**关键结论**：
> YoBot 现在的业务层是**硬编码成「商品销售」这一个场景**的。
> 数字分身要的不是「加六个页面」，而是**把业务层从销售专用重构为场景可配置**。
> 「私域销售」从此只是配置之一，而不是产品的隐含前提。

这条判断决定了整个工程的性质：**这是业务层重构，不是功能叠加。**

## 二、信息架构

> ⚠️ 注意：`product_plan.md` §2 给的是**六个**一级入口（今日｜人物｜事项｜时间线｜知识与技能｜分身 Wiki）；
> 而 `数字分身_Agent开发说明_v1.md` §2.1 给的是**五个**页面（今日 / 对话洞察 / 人物关系 / 事件时间线 / 我的记忆）。
> **两者不一致，需要拍板**（见 `05` 的 D0）。本文按六页面版本展开，因为原型实现的是六页。

| 一级页面 | 用户要解决的问题 | 页面主体 | 关键操作 |
|---|---|---|---|
| 今日 | 今天先做什么？昨天有什么变化？ | 昨日简报、三个行动、机会、承诺、洞察、Wiki 变更 | 切日期、看证据、开事项、导出简报 |
| 人物 | 与这个人聊到哪一步？要记住什么？ | 人物卡片 / 表格；详情与共同事项 | 搜索、按关系筛选、看证据、准备沟通 |
| 事项 | 哪些要做、等谁、何时完成？ | 待办、承诺、机会、项目、等待事项 | 处理、延后、暂停、核对完成、记录原因 |
| 时间线 | 一段时间里发生了什么？ | 以**业务事件**组织的时间线 | 按人／项目／类型筛选、展开原文 |
| 知识与技能 | 哪些经验值得保存和复用？ | 知识、反馈、方法、候选技能与验证记录 | 看依据、修订、验证、引用 |
| 分身 Wiki | 系统如何理解我？依据与权限是什么？ | 九维索引、条目、候选变更、版本、关联证据 | 确认、修订、否定、标记例外、限制用途 |

全局能力放页头：**搜索、问分身、数据与设置、撤销／历史**。

**去重原则**：「人物」与 Wiki 的「关系」、「知识与技能」与 Wiki 的「知识体系」**共用同一实体**，是不同入口而不是两份资料。

## 三、三个闭环

| 闭环 | 链路 |
|---|---|
| **事项闭环** | 聊天 → 事实与事件 → 人物／项目／机会／承诺 → 建议 → 本人处理 → 结果核对 → 更新状态 |
| **知识闭环** | 重复问题或有价值的解决过程 → 知识／方法／技能候选 → 关联证据 → 本人确认／实际验证 → 复用与修订 |
| **分身闭环** | 本人表达及经历 → 九维候选理解 → 证据与例外 → 审核 → 正式记忆 → 任务调用 → 纠错与版本更新 |

三条闭环有共同骨架：**候选 → 证据 → 本人确认 → 可用 → 纠错**。这条骨架就是产品与"自动摘要器"的分界线。

## 四、今日页与日报规则

### 4.1 日报输入不只昨天

综合三个来源：**昨日新增事件 + 历史未闭环事项 + 当前目标与业务规则**。
输出必须区分「昨日发生」「历史遗留」「今天到期」。**历史旧消息补导入不能显示成今日新进展。**

### 4.2 五段结构

1. **今日最该做的三个动作** —— 每项含：对象/关联事项、为什么现在做、具体动作、期望推进、时间依赖、建议回复、证据链接、处理状态。**证据不足或只剩两件时允许少于三件。**
2. **昨日聊天总览** —— 首次出现联系人 / 活跃会话 / 有效业务会话 / 新增机会 / 事项变化 / 待处理。**消息数量与业务价值分开；统计由确定性程序算，模型负责解释。**
3. **值得推进的机会** —— S/A/B（定义见 §五）。**评级对象是「联系人或组织 × 具体产品或目标 × 本次机会」，不是一个人的永久标签。**
4. **反馈与洞察** —— 每条固定：观察 → 证据范围 → 价值 → 建议 → 验证方式。证据充足时 3–7 条，**不足时不凑数**。
5. **未闭环事项与分身更新** —— 到期承诺、未答问题、等待材料、交付风险、Wiki 变更。**分身没有新证据时不强行生成更新。**

### 4.3 每份日报必须带的元信息

日期区间、时区、数据范围、同步截至时间、未解析媒体／附件缺口、生成时间、报告版本、是否修订。

> 「未见付款记录」**不等于**现实中未付款。涉及线下渠道时，行动前提示核对。

### 4.4 推送与网页分工

推送只发短摘要（三个行动、紧急承诺、重要变化、网页入口）；网页承载完整原文与操作。
**已推送报告要留快照**；人工纠正后生成修订版，**不能静默改写过去**。

## 五、人物、机会与事项

### 5.1 机会分级

| 等级 | 定义 |
|---|---|
| **S 优先推进** | 目标高度匹配，有实质采购推进动作，关键条件有足够证据 |
| **A 重点验证** | 痛点与范围具体，持续围绕落地追问，但关键条件有缺项 |
| **B 持续培育** | 方向相关，但需求／预算／时间／意愿仍模糊 |
| 待确认 | 有迹象，但证据不足以认定 |
| 暂停／排除 | 明确拒绝、不匹配、要求稍后联系 |

**禁止**：仅因回复、活跃、单次询价或购买低价产品，就把另一项机会认定为 S。
缺失信息写「预算未确认」，**不能写成「预算不足」**。

### 5.2 必须分清的四个对象

**联系人 / 组织 / 机会 / 任务**。一家公司可能有多位联系人，一个人可能有多项机会。
**昵称相同不能直接合并**；身份合并建议应可由本人检查并撤销。

### 5.3 事项状态

- 建议状态：已生成 / 已采纳 / 已修改 / 已拒绝
- 业务状态：待处理 / 等待对方 / 已执行待核对 / 已闭环 / 暂停 / 取消
- **生成草稿 ≠ 已发送；收到任意回复 ≠ 完成全部承诺**
- 完成依据来自具体执行记录、相关业务记录或本人确认，并写明依据

## 六、九维分身 Wiki

### 6.1 结构原则

**九维是索引，不是九个互不相通的文件夹。** 同一实体只维护一份内容，用关联关系连接维度、经历、人物、方法与资源。

| 维度 | 记录范围 | **必须保留的边界** |
|---|---|---|
| 世界观 | 本人对因果、变化、不确定性、个人与环境的理解 | 保留语境与变化，不简化成性格标签 |
| 意识形态 | 本人**主动提供并明确确认**的社会/制度/组织主张 | **不从转发、群聊、关系或行为推断政治信念** |
| 知识体系 | 知识地图、领域、方法、资料、实践与盲点 | **收到文章不等于读懂；已收录不等于已掌握** |
| 思维方式 | 问题拆解、证据要求、判断步骤、修正方式 | **一次行为不自动升级为长期特征** |
| 价值体系 | 本人确认的优先级、原则、底线、取舍与例外 | 分清历史行为、认可原则、成长目标 |
| 身份 | 当前角色、组织归属、职责、权限与对外介绍 | 角色名**不等于**系统操作授权 |
| 履历 | 经历、时间、实际角色、行动、结果 | **区分参与、主导、转述；不虚构成果** |
| 关系 | 相识背景、共同事项、承诺、互动与边界 | **认识不等于能调用资源** |
| 资源 | 自有/授权/可申请的能力、资产、工具、渠道 | 记录归属、条件、**有效期**和是否实际获准 |

### 6.2 条目模板（关键字段）

条目编号与标题（**不因改名丢失引用**）、维度/类型（**支持多维引用**）、当前结论（**拆成可逐条确认的命题**）、信息性质、证据、适用范围、**例外与冲突**、时间（发生/有效/最后确认/导入）、状态、**允许用途**、关联、修订与确认记录。

**状态取值**：候选 / 已确认 / 存在冲突 / 待更新 / 已否定 / 已归档

### 6.3 更新规则

1. 新聊天形成候选后，**先查已有条目**，再提议新增／补充／冲突／更新
2. 低风险事件可自动建**带来源的候选**；**高层个人理解不直接变成正式长期记忆**
3. 涉及转发、引用、玩笑、谈判情境、第三方观点或 AI 草稿时，**必须区分来源主体**
4. **未经本人认可的 AI 输出，不能反过来成为「本人观点」的证据**
5. 已确认条目的新改动进入**待审核版本**，旧版本保留时间与上下文

### 6.4 私人分身与对外助手

私人分身用本人授权的内部记录；对外助手**只检索批准公开的资料**，并明确它是助手。
隐私控制须覆盖**正文、摘要、标题、反向链接、检索索引、附件和版本** —— 不是给页面加"私人"标签就完事。

## 七、问分身的调用方式

> 分身回答应来自「**当前任务 + 相关条目 + 最新事实 + 当前目标 + 权限**」，**不是**把全部聊天和九维正文拼成一个无限增长的提示词。

典型任务：回忆背景、检查承诺、会前速读、准备回复、寻找过往经验、比较行动路径、检索匹配资源。

**约束**：
- 分身不应把「我可能会怎么处理」包装成「我已经作出决定」
- 对政治选择，**不使用个人画像做定向引导或替本人决策**
- 输出中须显示：事实、参考条目、**未知信息**、需要本人决定的部分

## 八、设计规范（原型已实现，需落成 token）

### 8.1 视觉方向

白底、居中内容、顶部文字导航、**黑色选中状态**、圆角筛选标签、细边框卡片、灰色辅助信息、**少量紫色链接**。

**不采用**：宽大左侧菜单、彩色指标大屏、密集图表、九个雷达图、全屏聊天框、复杂关系网络（关系图可作后续辅助视图，不是首页）。

### 8.2 建议尺寸

| 元素 | 值 |
|---|---|
| 顶栏高 | 64–72 px |
| 主内容 | 居中，最大宽 1040–1120 px |
| 页标题 | 26–28 px |
| 一级导航 | 15–17 px，选中项黑色底线 |
| 二级筛选 | 胶囊形，选中黑底白字 |
| 卡片 | 白底、1px 浅灰边、10–12px 圆角、**无重阴影** |
| 卡片标题 | 16–18 px |
| 正文 | 14–16 px，行高 1.7–1.9 |
| 元信息 | 12–13 px 灰；**不把重要警告藏在低对比文字里** |
| 详情抽屉 | 桌面 560–640 px；手机全宽 |

### 8.3 必须设计的异常状态（12 种）

首次空白数据、正在导入、同步失败、部分日期缺失、语音／附件未解析、身份可能重复、条目存在冲突、暂无证据、候选被否定、任务已在其他渠道处理、权限不足、已暂停的对外执行。

> **不要在缺少数据时展示看似真实的「零客户、零机会」作为确定事实。**

## 九、首版明确不做

自动发消息、群发、发圈、加好友、自动通讯录同步、自动改 RPA 配置、群内真实 @、头像采集、完整历史回填、实时消息监控、云端真实数据同步。

**全自动九维人格填充、全联系人心理画像、复杂三维关系图、未经验证的"成交概率"、一次性覆盖所有行业的复杂工作流** —— 这些也不在首版。

> 微信写操作**不因界面上有"确认"按钮就自然获得授权**。首版只开放**本应用内部**的任务、备注、记忆、草稿与偏好写入。
