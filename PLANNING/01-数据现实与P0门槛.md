# 数据现实与 P0 门槛

> **这份文档的存在理由**：`DIGITAL-TWIN/product_plan.md` 的起点写的是「已有本地机器人能够取得微信历史与每日聊天记录」。
> **这句话不成立。** 本机当前**没有任何一条落盘的微信聊天消息**。
> 在讨论「前端选 Vue 还是 React」「记忆层怎么做」之前，必须先把这个前提补齐，否则整份计划都是空壳。

本文所有状态均为 **2026-09-22 12:2x 本机实测**（含一次实机诊断，方法见文末附录），不是文档转述。

## 一、结论：采集链路只通了一半

不是「没有数据源」，是「采集链路半通」。这是本计划最重要的一条判断：

```
微信客户端在线 ✅
    ↓
界面自动化可用 ✅        （RPA 真的读到了群消息）
    ↓
★ 断点一：读到的消息没有落盘 ❌    （chat_history/ 目录不存在）
    ↓
★ 断点二：通讯录同步循环失败 ❌    （18 条失败，14 条是 AX 定位失效）
    ↓
数字分身六页面拿不到数据 ❌
```

## 三、通讯录同步失败的根因（已定位）

18 条 `contact.sync.failed` 的 `result.error_message` 分布：

| 次数 | 错误信息 | 含义 |
|---|---|---|
| **14** | `the single row click did not expose a verified focused remark field` | **点击好友行后，找不到被聚焦的「备注」输入框** |
| 2 | `WeChat has no AXMainWindow for contact reading` | 读不到微信主窗口的 AX 节点 |
| 1 | `the current semantic WeChat main window did not become focused within the bounded wait` | 有界等待内主窗口未取得焦点 |
| 1 | `macOS Helper IPC exchange failed: timed out` | 原生 Helper 通信超时 |

**判读**：14 条是同一类失败 —— RPA 用 Accessibility API 定位微信界面元素，**微信的 AX 结构变了，原有选择器失效**。

这不是配置错误，是**对抗性赛道的结构性症状**：RPA 靠界面元素定位工作，微信每次升级都可能打破它。同一症状在 `sync_contacts_manager.log` 里表现为**几十次「启动成功 → 停止成功」的循环**（09-21 12:39 至 09-22 09:54），每次起来就跑不通。

> ⚠️ **但它并没有全坏**：09-21 11:53 的 auto_reply 日志证明它**读到了群消息**。所以「能读」这条链是活的，「同步/落盘」那条链是死的。这个区分对定位问题很关键 —— 不要把两者混为一谈。

## 四、落盘为什么不产出（未完全定论）

已确认：`chat_history` 目录从未被创建。但**尚未确认原因**，候选有三，需要在本机逐一排除：

| 候选原因 | 怎么证伪 |
|---|---|
| A. `chat_history_settings` 配置未开启或未生效 | 检查 YoBot 侧 `chat_history_settings` 配置项的实际值 |
| B. 落盘依赖「通讯录同步」成功后才启动 | 观察修好同步后落盘是否自动开始 |
| C. 落盘功能本身在恢复版里不完整 | 检查 `recovery-mcp.js` 与 RPA 侧落盘模块的实际路径映射 |

本节按 `微信数据对外接入文档.md` 的口径**不写结论** —— 那是 P0 要做的事。

## 五、P0 门槛：什么算通过

沿用 `数字分身_Agent开发说明_v1.md` §5 的方法，但把目标从「建一个外挂应用」改为「让 YoBot 产出可用数据」。

### P0 交付物

1. `capability_report.local.json` —— 环境可达性、允许读取的账号、工具实际 `inputSchema`、各数据源存在性
2. `field_mapping.md` —— 历史消息响应的**真实字段结构**（脱敏后的 fixture）
3. **采集链路诊断报告** —— 三个断点各自的原因与处置

### P0 通过标准

- [ ] 连接 `initialize` 成功，保存协商出的协议版本与 `serverInfo`
- [ ] `tools/list` 拿到 7 个工具的实际 schema，与 `微信数据对外接入文档.md` §2.4 逐条比对
- [ ] 只读白名单固定为 5 个工具；`wechat_send_message` / `wechat_sync_contacts` 的调用次数为 **0**
- [ ] 拿到**至少一条真实会话索引**（`wechat_list_history_sessions` 非空）
- [ ] 拿到**至少一条可溯源的真实消息**，明确其账号归属、发生时间、说话者/方向及其缺失状态
- [ ] 三个断点各自得出「已定位 / 未定位」的明确结论
- [ ] 未读取 `protected/agent-secrets.v1.json`，未把 token 写入任何文件、日志或提示词

> **允许 P0 结论是「聊天未就绪」。** 这是合格诊断，不是失败。但不允许用虚构数据把它糊过去。

### P1 门槛（产品可用的最低线）

在有真实消息之后，逐级开放能力 —— **不要跳级**：

| 已有的 | 才能做 |
|---|---|
| 正文 + 来源 | 展示片段与人工标注 |
| 另有可靠时间 | 进入对应日期的时间线与范围统计 |
| 另有我方/对方判定 | 提取承诺候选与待响应候选 |
| 有跨会话可验证身份 | 独立人物统计与跨对话聚合 |
| 有足量样本 + 配置 | 有依据的洞察与机会建议（**不以消息条数代替质量判断**） |

## 六、对产品计划的三条硬约束

1. **不得用虚构数据冒充真实日报。** `product_plan.md` §10.7 已写明这条；本机现状让它的重要性上升为第一约束。
2. **不得把「工具存在」当成「消息存在」。** 7 个 MCP 工具都在，但索引可能是空的。
3. **产品方案里的 S/A/B 机会分级、Top 3 动作、九维 Wiki 自动候选，全部依赖真实消息。** 在 P1 通过前，这些页面只能出**空状态 + 人工录入**版本。

## 七、绕不过去的一个战略问题

即使把通讯录同步修好、落盘打通，仍然存在一个更根本的问题：

> **RPA 采集的可靠性能撑住一个「记忆类产品」吗？**

`product_plan.md` 的产品主张是「把日常沟通变成可追溯的记忆」。而记忆类产品对**召回完整度**的要求极高 —— 漏掉一条承诺，用户就会失去信任。

但上游的能力边界是（`微信数据对外接入文档.md` §6）：

| 口径 | 实际含义 |
|---|---|
| 落盘历史 | **机会式采集**，可能有缺口，不是连续录制 |
| 当前窗口快照 | 只约 5 条，只读当前聊天窗可见的最后一屏 |
| 会话索引 | 只有「被采集过」的会话才在索引里 |

**这是本计划最大的产品风险，且它不是技术问题。** 建议在 P0 阶段同步做一个「采集覆盖率实测」：连续运行若干天，统计「微信里实际发生的会话」与「落盘到的会话」的比值。这个数字决定数字分身的**产品定位**（是「可靠的记忆」还是「某些场景下的辅助」）。
