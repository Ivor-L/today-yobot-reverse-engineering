## 零、一页速览

**一句话**：把日常沟通变成**可追溯的记忆、可处理的事项、可复用的知识**，逐步形成由本人确认和控制的数字分身；这套认知能力建在 YoBot 已有的渠道与执行引擎之上，销售只是它的场景配置之一。

**三层架构（不是三个产品，是一个产品的三层）**

```
┌─────────────────────────────────────────────────────────┐
│  认知层   今日 · 人物 · 事项 · 时间线 · 知识与技能 · 分身 Wiki   │
├─────────────────────────────────────────────────────────┤
│  记忆层   私人记忆：Markdown VFS + 版本快照 + 可浏览资产         │
│  知识层   世界知识：解析 → 混合检索(RRF) → 精排 → Wiki 溯源      │
│           ↑ 两者数据模型分开，检索通道分开                      │
├─────────────────────────────────────────────────────────┤
│  执行层   YoBot 引擎：agent / scheduler / channels / 插件       │
│  数据层   微信 RPA · iLink · 飞书 · WS（只读适配器）             │
└─────────────────────────────────────────────────────────┘
```

**六个一级页面**：今日｜人物｜事项｜时间线｜知识与技能｜分身 Wiki

**三条闭环**（共用骨架：候选 → 证据 → 本人确认 → 可用 → 纠错）：事项闭环｜知识闭环｜分身闭环

**一句话记住记忆与知识的分工**：
> **世界知识进检索（找得到），私人记忆走文件（说得准）。**

## 一、产品定位

### 1.1 它是什么

一个**本地优先的个人认知系统**：把散落在聊天、文档、图片里的信息，沉淀成可以被人阅读、被人修订、被 Agent 调用的结构化资产。

它不是：聊天摘要器、销售后台、通用 RAG 问答机器人。

### 1.2 它和 YoBot 的关系

**同一底座，不同场景配置。**

YoBot 现有 10 个页面（客户管理 / 朋友圈 / 自动 SOP / 群发 / 加好友）**全部是销售动作**——业务层被硬编码成「商品销售」一个场景。数字分身要的不是"再加六个页面"，而是把业务层从销售专用重构为**场景可配置**：

| 场景 | 重点字段 | 不宜混用的标准 |
|---|---|---|
| 商品销售 | 规格、数量、预算、采购角色、交付时间 | 购买某商品不代表对另一商品有高意向 |
| 项目／服务 | 目标、范围、流程、角色、预算、验收 | 不凭泛泛咨询认定可成交 |
| 合作共创 | 共同目标、分工、双方投入、下一步 | 不以采购预算作唯一判断依据 |
| 内部协作 | 负责人、依赖、交付物、阻碍、期限 | **不给同事设销售意向等级** |
| 个人事务 | 约定、待回复、共同事项、提醒边界 | **不把朋友纳入商业评分** |

**「私域销售」从此是配置之一，而不是产品的隐含前提。**

### 1.3 定位张力与解法

产品方案 §1 明确写着「不应只是聊天摘要器，也不是把所有联系人当成客户的销售后台」，而 YoBot **就是**销售后台。解法在方案 §1.3：**统一底层对象，把场景字段与规则放入配置**。

**这条判断决定了工程性质：这是业务层重构，不是功能叠加。**

工程上对应一个动作（见 `05` D1）：**销售能力不消失，但从产品骨架降为「人物/事项详情里可调用的动作」。** 六页是一级入口，群发/加好友/朋友圈变成动作按钮。

## 二、最终架构：三层

### 2.1 为什么是三层，不是三个产品

三轮核验得出的结论：**YoBot 的向量库、Today 的记忆范式、WeKnora 的知识框架，解决的是三个不同的问题，不是同一个问题的三个答案。**

| | 解决的问题 | 本质 | 归属层 |
|---|---|---|---|
| YoBot `memory/` | 从海量文本里**捞出相关片段** | 检索（Retrieval） | **降级为索引能力** |
| Today 记忆范式 | 关于人/关系的**长期认知如何沉淀** | 记忆（Memory） | **记忆层主干** |
| WeKnora Wiki | 外部知识的**解析、检索、溯源、协同编辑** | 知识（Knowledge） | **知识层** |

### 2.2 各层的构成明细

**执行层（复用 YoBot）**

| 模块 | 文件数 | 作用 |
|---|---|---|
| `agent/` | 145 | 会话编排、上下文裁剪（pruner）、任务、专家系统、harness |
| `scheduler/` | 9 | 执行预设 / 变更意图 / 结果，日报与 Wiki 候选的定时底座 |
| `channels/` | 11 | 微信 · iLink · 飞书 · WebSocket 四条推送出口 |
| `skills/` | 72 | MCP 客户端 + 服务端、工具、用户安装目录 |
| `electron/` | 53 | 插件系统、更新、安全、窗口 IPC |

**记忆层（Today 范式为主干）**

- Markdown 虚拟文件系统为存储，`MemoryActivity{file{path,version}, snapshot{version,content}}` 记录历史版本
- 记忆是**可浏览的资产**（文件夹 / 重命名 / 排序 / pin / Highlights），不是设置项
- 提炼是**一种任务**（`taskType: build_up_memory`），定时跑，不实时写入
- 写入权规则：**候选由 Agent 提，确认权归本人**
- 调用时接 YoBot 的召回 + 判决 + 注入闸门（阈值 0.48/0.55，三层预算 2600/1200/4000 字符）

**知识层（WeKnora Lite）**

- 解析：26 个解析器，覆盖 pdf（含扫描件）、doc/docx、xlsx/csv、**ppt/pptx**、html/mht、md、epub、xmind、图片
- 检索：向量召回 50 → 与关键词双路**RRF 融合**（k=60，向量 0.7 / 关键词 0.3）→ **独立 rerank 模型精排** → top 10
- Wiki：`wiki_pages`（Markdown + 树形层级 + 双向链接 + `source_refs` 反向溯源到原文分块）+ `wiki_page_revisions`（不可变快照，可 diff 可回滚）+ `last_edit_source`（记录这一版是谁写的）
- 部署：`DB_DRIVER=sqlite` + `RETRIEVE_DRIVER=sqlite`（FTS5 + sqlite-vec），**无需 Docker 全家桶，可打包成桌面 .app**

### 2.3 层间接口

**知识层通过 MCP 接入，对执行层零侵入。** YoBot 有 MCP 客户端（`skills/mcp/`），WeKnora 有 MCP server（`ask` / `ingest` / `retrieve` / `wiki` 四组工具）。语义天然吻合，不需要写胶水层。

## 三、记忆与知识的分工（本文最关键的一节）

**这是最容易搞混、一旦混了产品就废掉的地方。**

### 3.1 两个目标方向相反

| | 私人记忆 | 世界知识 |
|---|---|---|
| 用户要的是 | **权威复述**（"我说过的话要能准确复述"） | **相似召回**（"相关的内容要能找到"） |
| 失败形态 | 想起来的是**相近的**，不是**真实的** | 找不到、排在太后面 |
| 存储 | Markdown 文件 + 版本 | 向量库 + 全文索引 |
| 可编辑 | **必须可编辑、可审计、可回滚** | 可重新摄取，不要求逐条可编辑 |
| 权威性 | 单条即真理 | 多条候选，需精排 |

WeKnora 自己的代码注释把知识库的取向写得很直白：`interest` 类型 *"exists to condition retrieval rather than to be quoted back at the user"*——**存在的意义是给检索加条件，而不是复述给你听**。

**所以：用向量召回取记忆，是结构性错配。** 对数字分身而言这是致命的。

### 3.2 数据模型必须分开

YoBot 现在的做法已经很接近了——它用 `isKnowledgePath()` 按 `knowledge/<ns>`、`agents/<name>/knowledge/<kb>` 前缀路由。但它底下是**同一张 LanceDB 表、同一条检索通道**。

**最终形态要改成两条独立的路径：**

```
私人记忆  →  文件系统直读（准确、可版本、可浏览）
世界知识  →  索引召回（向量 + 关键词 + rerank）
```

不是一个阈值调参的事，是两套读写通道。

### 3.3 YoBot 向量栈的最终位置

**不拆、不改写，但重新定位。**

`memory/` 那 14 个模块里，有一部分资产是要花时间才能攒出来的，尤其：

- 召回阈值用 **45 组真实 query→memory 对**校准过（0.48 / 0.55，注释里记着上一版 0.62「不可达」）
- `recall_judge`（LLM 判决）、`injection_gate`（注入闸门）、三层 token 预算
- `signal_processor`、`evolution`、各类 extractor

代码注释里甚至有一句很清醒的话：*"它占据候选位、占用 embedding 配额、进 BM25 倒排，却不可能对任何回答有帮助"*——说明做过污染控制。

**结论：这套降级为「知识层的检索实现之一」，与 WeKnora 并存或逐步替换。它不再承担「记忆」的职责。**

## 四、信息架构

### 4.1 六个一级页面

| 一级页面 | 用户要解决的问题 | 页面主体 | 关键操作 |
|---|---|---|---|
| **今日** | 今天先做什么？昨天有什么变化？ | 昨日简报、三个行动、机会、承诺、洞察、Wiki 变更 | 切日期、看证据、开事项、导出简报 |
| **人物** | 与这个人聊到哪一步？要记住什么？ | 人物卡片 / 表格；详情与共同事项 | 搜索、按关系筛选、看证据、准备沟通 |
| **事项** | 哪些要做、等谁、何时完成？ | 待办、承诺、机会、项目、等待事项 | 处理、延后、暂停、核对完成、记录原因 |
| **时间线** | 一段时间里发生了什么？ | 以**业务事件**组织的时间线 | 按人／项目／类型筛选、展开原文 |
| **知识与技能** | 哪些经验值得保存和复用？ | 知识、反馈、方法、候选技能与验证记录 | 看依据、修订、验证、引用 |
| **分身 Wiki** | 系统如何理解我？依据与权限是什么？ | 九维索引、条目、候选变更、版本、关联证据 | 确认、修订、否定、标记例外、限制用途 |

> 页面集合为什么是六个：`product_plan.md` §2 与原型都是六页，只有开发说明是五页（那份文档关注点在数据接入，页面是顺带写的）。

**全局能力**放页头：搜索、问分身、数据与设置、撤销／历史。

### 4.2 去重原则（六页能否站得住的关键）

- 「人物」的关系维度 与 「分身 Wiki」的关系维度 → **同一实体，不同入口**
- 「知识与技能」 与 「分身 Wiki」的知识体系 → **同一实体，不同入口**
- **多入口是负债**——每多一个入口，就多一整套「切过去时上下文怎么带」的问题（这是从 Today 单时间线改版里学到的判断）

### 4.3 视觉方向

白底、居中内容、顶部文字导航、**黑色选中状态**、圆角筛选标签、细边框卡片、灰色辅助信息、少量紫色链接。

**不采用**：宽大左侧菜单、彩色指标大屏、密集图表、九个雷达图、全屏聊天框、复杂关系网络。

| 元素 | 值 |
|---|---|
| 顶栏高 | 64–72 px |
| 主内容 | 居中，最大宽 1040–1120 px |
| 页标题 | 26–28 px |
| 一级导航 | 15–17 px，选中项黑色底线 |
| 卡片 | 白底、1px 浅灰边、10–12px 圆角、**无重阴影** |
| 正文 | 14–16 px，行高 1.7–1.9 |
| 详情抽屉 | 桌面 560–640 px；手机全宽 |

**必须设计的 12 种异常状态**：首次空白数据、正在导入、同步失败、部分日期缺失、语音／附件未解析、身份可能重复、条目存在冲突、暂无证据、候选被否定、任务已在其他渠道处理、权限不足、已暂停的对外执行。

> **不要在缺少数据时展示看似真实的「零客户、零机会」作为确定事实。**

## 五、三条闭环

三条闭环有共同骨架：**候选 → 证据 → 本人确认 → 可用 → 纠错**。这条骨架就是产品与「自动摘要器」的分界线。

| 闭环 | 链路 |
|---|---|
| **事项闭环** | 聊天 → 事实与事件 → 人物／项目／机会／承诺 → 建议 → 本人处理 → 结果核对 → 更新状态 |
| **知识闭环** | 重复问题或有价值的解决过程 → 知识／方法／技能候选 → 关联证据 → 本人确认／实际验证 → 复用与修订 |
| **分身闭环** | 本人表达及经历 → 九维候选理解 → 证据与例外 → 审核 → 正式记忆 → 任务调用 → 纠错与版本更新 |

**事项状态机**（比方案原文六态更完整，借鉴 Today）：

- 建议状态：已生成 / 已采纳 / 已修改 / 已拒绝
- 业务状态：待处理 / 等待对方 / 已执行待核对 / 已闭环 / 暂停 / 取消
- 结果态：`success / partial / degraded / failed`（**后两态是「部分成功」的表达需要**）
- **`pending_user_answer`**：任务能中途停下来问人
- **生成草稿 ≠ 已发送；收到任意回复 ≠ 完成全部承诺**

## 六、能力矩阵：输入格式（最终承诺）

**这一节直接决定「资料上传」的产品承诺怎么写。**

三层同时存在时，格式能力按「谁解析」分工：

| 格式 | 现状（YoBot） | 最终形态 | 由谁提供 |
|---|---|---|---|
| PDF（文本版） | ✅ 三通道 | ✅ | 已有 |
| **PDF（扫描件）** | ❌ **不做 OCR**，正文<20 字符即判失败 | ✅ | **WeKnora**（PDFScannedParser） |
| DOCX | ✅ | ✅ | 已有 |
| DOC（旧版） | ❌ | ✅ | WeKnora |
| XLSX / CSV | ✅（有截断坑，见下） | ✅ | 已有 + WeKnora |
| **PPT / PPTX** | ❌ **一个入口都没有** | ✅ | **WeKnora**（MarkItDown） |
| TXT / MD / JSON | ✅ | ✅ | 已有 |
| 代码（js/ts/tsx） | ✅ | ✅ | 已有 |
| `.fireflow`（自研） | ✅ | ✅ | 已有 |
| HTML / MHT | ❌ | ✅ | WeKnora |
| EPUB / XMind | ❌ | ✅ | WeKnora |
| 图片 PNG/JPG/GIF/WEBP/BMP | ✅ 多模态，非 OCR | ✅ | 已有 |
| 图片 HEIC / TIFF / SVG | ❌ | 待定 | 需评估 |
| 语音 | ❌ 未解析 | 待定 | 不在首版 |

### 6.1 三条上传通道的差异（现状，会影响产品设计）

| 通道 | 白名单 | 限制 | 模式 |
|---|---|---|---|
| **Agent 对话附件** | 仅 `pdf / docx / xlsx` | 5 文件 / 单文件 10 MB / 2.4 万字符；Excel **有界预览**（超 400 单元格截到 12 行 × 20 列） | 预览 |
| **微信收到的文件** | `pdf / docx / xlsx / txt / md / json / .fireflow / js / ts / tsx` | 硬校验文件头（PDF 查 `%PDF-`、Office 查 `PK`、文本查 `\0` + UTF-8 严格解码） | 直读 |
| **知识库上传** | 同上 9 种 | 单文件 **50 MB** | **`mode:'ingest'` 全量不截断** |

> ⚠️ **通道①与③的差异是一颗雷**：拿预览模式做摄取会把大表格静默截断——用户传了 5000 行报价表，索引里只有前 12 行，**检索永远搜不到第 13 行以后，且毫无报错**。
> **最终形态必须统一走 `ingest` 全量模式。**

### 6.2 两个事故记录，要写进设计约束

**① 扫描件 PDF 曾被当成功入库。** 以前是把一句英文警告**拼进 content**，结果 content 从"空"变"非空"，调用方只判 `chars === 0`，于是这份文档被当解析成功入库——用户看到"导入成功"，RAG 里躺着的其实是一句报错，检索时还会被召回。
→ **约束：失败必须是结构化的失败态，不能靠内容非空来表达成功。**

**② 一张 22 MiB 的图永久毒化了会话。** 用户传了大图，**两天后**问一个跟图毫无关系的问题照样 400——因为图还在会话历史里，每轮都重发。
→ **约束：大附件必须降采样 + 会话历史里的附件要有生命周期。**

## 七、主动动作体系

YoBot 已有 `scheduler/`（执行预设 / 变更意图 / 结果），**机制在，缺的是产品化形态与反馈维度**。

### 7.1 六种形态

| 形态 | 说明 |
|---|---|
| `automation` | 定时/一次性任务（cron / once） |
| `task_recommendations` | 可一键 apply 的建议 |
| `asst_proactive` | Agent 主动发起的消息 |
| `live widgets` | Agent 可主动编辑的实时组件 |
| `brief` | 晨报 / 晚报 |
| `day_in_progress` | 今日进展，**可被回复** |

### 7.2 最值得抄的一条：三维反馈

主动消息的反馈是三维的：`helpfulness / factualAccuracy / **timing**`。

> **把「打扰」单列成一个可优化的错误类型**——这是主动型产品与通知系统最本质的区别。

数字分身「今日」页的三个动作、紧急承诺、重要变化，**每一条都该带 timing 反馈**。

### 7.3 推送与网页分工

推送只发短摘要（三个行动、紧急承诺、重要变化、网页入口）；网页承载完整原文与操作。
**已推送报告要留快照**；人工纠正后生成修订版，**不能静默改写过去**。

## 八、数据通道与合规边界

### 8.1 三条数据通道

| 通道 | 形态 | 鉴权 | 数字分身是否使用 |
|---|---|---|---|
| **A. MCP 网关** | Streamable HTTP，`POST 127.0.0.1:<随机端口>/mcp` | Bearer | **首选**（在线读取） |
| **B. RPA HTTP API** | FastAPI，`127.0.0.1:9922` | `X-API-Key`（**进程内临时凭据，外部拿不到**） | ❌ 不使用 |
| **C. 本地文件** | SQLite / JSONL | 文件权限 | 使用（离线取数、诊断） |

**MCP 工具白名单（7 个中只用 5 个只读）**：`wechat_status`、`wechat_list_history_sessions`、`wechat_get_history_messages`、`wechat_list_contacts`、`wechat_list_groups`。

不使用：`wechat_sync_contacts`（有副作用，会驱动桌面微信）、`wechat_send_message`（不可撤销，**不进首版**）。

### 8.2 不能对外承诺的能力边界

| 想要的 | 实际 | 结论 |
|---|---|---|
| 每个好友的头像 | 表里无头像列，同步流水线不持久化 | ❌ 拿不到 |
| 实时监控群消息 | 只有机会式采集的落盘历史 | ❌ 无实时流 |
| 群聊里 @ 某人 | RPA 无 @ 发件人能力（写 `@张三` 只是文字） | ❌ 做不到 |
| 完整微信历史 | 不读 `WeChat Files`，只有被采集过的部分 | ❌ 只有片段 |

### 8.3 合规边界（隔离而不扩散）

- 数据层设计成**可替换的适配器接口**：上游是 MCP 网关还是未来官方通道，接口不变
- **隔离对 `recovery-mcp.js`（逆向加装组件）的依赖**——不把实现细节泄漏进业务层
- 首版可以依赖它，但**交付物里不包含逆向组件**（`standalone/scripts/` 下的授权绕过脚本不得随产品分发）
- 微信写操作**不因界面上有"确认"按钮就自然获得授权**；首版只开放**本应用内部**的写入
- 仓库**不能设为公开**（含本机路径、端口、进程名、逆向组件）

### 8.4 一个被搁置但值得单独拍板的机会

WeKnora 自带 `internal/im/`，有微信、企微、飞书、钉钉、Slack、TG、QQ、云之家渠道——**但它接的是 API 可达的公众号/企微，YoBot 走的是个人号 RPA（协议外逆向）**，合规性质完全不同。

> 如果客户能接受「客服号」而不是「个人号」，YoBot 的微信层可能整套都不需要——**这能一次性解决合规问题。**

## 九、首版明确不做

**销售动作类**：自动发消息、群发、发圈、加好友、自动通讯录同步、自动改 RPA 配置、群内真实 @、头像采集。

**数据类**：完整历史回填、实时消息监控、云端真实数据同步。

**智能类**：全自动九维人格填充、全联系人心理画像、复杂三维关系图、未经验证的"成交概率"、一次性覆盖所有行业的复杂工作流。

**技术类**：不做通用 GUI Agent（失败率高）；不迁 Next.js 全栈内嵌（与本地 License 冲突且违反数据不出本机）；不上 Docker 全家桶（走 Lite 模式）。

### 10.1 唯一能立刻开始、不依赖任何大决策的工作

把 `product_plan.md` §10.3 的尺寸表 + 原型的实际 CSS 值，抽成一份 **CSS 变量 token 层**。

无论前端选 Vue 还是 React、无论 D1–D7 怎么定，**这一步都要做**，且能立刻验证「统一设计语言」长什么样。

### 10.2 零消息也能推进的三页

**事项、知识与技能、分身 Wiki** 三页可以在没有任何真实消息的前提下，用**人工录入的数据**跑通完整闭环（状态机、证据链、确认流、版本回滚）。

> 这是 P0 期间唯一能并行推进的产品工作——**「数据没打通」不等于「什么都做不了」**。

## 附：本文档的三条核心判断（供交叉验证用）

1. **数字分身是一次业务层重构，不是功能叠加。** YoBot 业务层写死成销售，数字分身要的正是这层通用化。

2. **记忆与知识必须分成两条通道。** 用相似度取记忆，会出现"想起来的是相近的，不是真实的"——对数字分身是致命的。

3. **最大的风险不在代码，在数据。** 不是"没有数据源"，是"采集只通了一半"：能读消息，但不落盘；通讯录同步因微信 AX 结构变化而失效（14/18 条失败的根因是 `the single row click did not expose a verified focused remark field`）。

> **在采集覆盖率实测出来之前，任何关于产品定位的承诺都是空的。**
