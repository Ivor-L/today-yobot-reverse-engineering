# 结合方案与决策地图

> 本文是把三份材料合起来之后，**新增的那一层判断**。
> `DIGITAL-TWIN/` 是输入，`01`–`04` 是事实与参照，**这份是方案**。

---

## 一、结合点在哪：数字分身是 YoBot 的一次业务层通用化

三份材料看起来在讲三件事，其实指向同一个动作：

```
product_plan.md        说「要什么」   →  六个页面 + 九维 Wiki + 三个闭环
微信数据对外接入文档     说「有什么」   →  5 个只读 MCP 工具 + SQLite + JSONL
数字分身_Agent开发说明   说「怎么接」   →  只读适配器 + 自建应用 + P0–P4 门槛
```

**而 YoBot 缺的正是这层的通用化。** 它现有的 10 个页面（客户管理 / 朋友圈 / 自动 SOP / 群发）**全部是销售动作**，业务层是硬编码成「商品销售」单一场景的。

所以：

> **数字分身 = 把 YoBot 的业务层从「销售专用」重构为「场景可配置」，并在此之上长出六页通用表达。**
> 「私域销售」从此是**配置之一**，而不是产品的隐含前提。

这条判断同时解决了 `03` §1.1 那个定位张力 —— 不需要在「销售后台」和「个人助手」之间二选一，因为它们是同一底座的两个场景配置。

## 二、分层归属地图

图例：**复用** = 现有实现直接用 ｜ **扩展** = 有基础需补 ｜ **重构** = 结构调整 ｜ **新建** = 两边都没有 ｜ **隔离** = 存在但要防止依赖扩散

| 层 | YoBot 现状 | 数字分身需要 | 判定 |
|---|---|---|---|
| **数据采集** | 微信 RPA（界面自动化） | 落盘的真实消息 | **修复 + 扩展** ⚠️ 当前断点，见 `01` |
| **数据通道** | MCP 网关（逆向版加装） | 5 个只读工具 | **隔离** —— 包装成可替换的适配器 |
| **标准化模型** | 无 | 人物/会话/消息/证据/事项 | **新建**（`数字分身_Agent开发说明_v1.md` §8 已给草案，17 张表） |
| **业务层** | 销售专用（写死） | 五场景可配置 | **重构** ← 本方案的核心动作 |
| **记忆** | 检索式（向量召回 + LLM 判决 + 注入闸门 + 三层预算） | 检索 **+ 资产化**（可版本化、可浏览、有允许用途） | **融合**（`04` §四） |
| **知识/技能** | `knowledge/` 有配额与容量核算 | 知识/反馈/方法/技能四类 + 验证状态 | **扩展** |
| **调度** | `scheduler/`（执行预设 / 变更意图 / 结果） | 日报定时、检查任务、Wiki 候选整理 | **扩展** |
| **主动动作** | 无明确对应 | 六形态 + **timing 反馈** | **新建** ← 最值得抄 Today 的一块 |
| **Agent 编排** | `agent/` 145 模块（会话编排、pruner、expert、harness） | 「问分身」+ 事项提取 | **复用** |
| **专家系统** | `agent/expert/`（能力组合 + 灰度发布 + 路由守卫） | — | **复用**（差异化资产） |
| **渠道** | 微信 RPA / iLink / 飞书 / WS | 推送出口 | **复用**（护城河） |
| **插件系统** | `electron/` 有完整插件安装与生命周期 | 交付形态候选 | **复用**（见 D6） |
| **前端页面** | Vue 3，10 个销售页 | 数字分身六页 | **新建** |
| **设计系统** | Element Plus 主题 + 自定义 CSS | token 层 | **新建** ← 唯一能立刻开始、不依赖大决策的工作 |
| **契约** | 裸 HTTP（97 端点）+ WebSocket | 生成式契约 + 能力协商 | **改造**（从 `/dt-api/v1` 草案起步） |
| **多品牌白标** | 运行时 `channel_id` 品牌配置 | 不能破坏 | **保留**，且所有颜色必须走 token |

## 三、六页面的落地路径

每页标注**依赖什么数据**与**P1 前能不能做**：

| 页面 | 核心数据依赖 | P1 前能做吗 | 落地方式 |
|---|---|---|---|
| **今日** | 昨日事件 + 未闭环事项 + 当前目标 | ⚠️ 部分 | 数据结构与状态机先建；无消息时只显示**人工待办 + 数据状态说明** |
| **人物** | 好友表 + 消息里的说话者身份 | ⚠️ 部分 | 群目录（97 行）可先做，标 `identity_quality=name_only`；好友需同步修复 |
| **事项** | 承诺/待响应候选（需我方/对方判定） | ✅ 可先做 | **人工录入跑通状态机**，不依赖消息 |
| **时间线** | 事件发生时间 + 人物 + 来源 | ⚠️ 部分 | 四视图与日期切换先做；无时间记录进「时间待确认」 |
| **知识与技能** | 原文 + 人工材料 | ✅ 可先做 | 人工收录优先，**模型未配置时允许人工** |
| **分身 Wiki** | 本人事实 + 证据 + 修订 | ✅ 可先做 | 九维索引 + 审阅流先做；自动候选等 P1 |

> **这张表是本方案最实用的一页**：它说明「数据没打通」不等于「什么都做不了」。
> **事项、知识与技能、分身 Wiki 三页可以在零消息的前提下用人工数据跑通完整闭环。** 这是 P0 期间唯一能并行推进的产品工作。

## 四、决策点

### D0. 页面集合：六个还是五个？

`product_plan.md` §2 是**六个**（今日｜人物｜事项｜时间线｜知识与技能｜分身 Wiki）；`数字分身_Agent开发说明_v1.md` §2.1 是**五个**（今日｜对话洞察｜人物关系｜事件时间线｜我的记忆）。

| | 六页面版 | 五页面版 |
|---|---|---|
| 与原型的关系 | **原型实现的就是这一版**（`preview_wiki.png` 可见九维索引） | 与原型不符 |
| 覆盖 | 「事项」独立成页 | 事项被拆进今日与人物 |
| 九维 Wiki | 独立成页，有完整审阅流 | 名为「我的记忆」，弱化 |

**建议：六页面版。** 理由：原型是六页，产品方案是六页，只有开发说明是五页（那份文档的关注点在数据接入，页面是顺带写的）。
**代价**：多一个入口，需要确保「人物」与「Wiki 关系」、「知识与技能」与「Wiki 知识体系」不重复建设（`03` §二已给去重原则）。

### D1. 数字分身与现有 10 个销售页面怎么共存？

| 选项 | 说明 | 代价 |
|---|---|---|
| **A. 平级并列** | 导航从 10 项变 16 项 | 导航爆炸，两组功能气质冲突 |
| **B. 模式切换** | 「运营模式 / 分身模式」两套导航 | 用户需要理解两个世界；数据其实是一套 |
| **C. 数字分身为主，销售功能降为「动作」** | 六页是一级入口；群发/加好友/朋友圈变成「人物/事项详情里的动作按钮」 | **最符合 `product_plan.md` §1 的定位，且消解了张力**；但需要把销售功能从「页面」重构为「动作」 |

**建议：C。** 这是唯一能让「不做销售后台」这句话成立的方案 —— 销售能力不消失，但从**产品的骨架**降为**场景配置下可调用的动作**。
**风险**：这是最大的一次结构改动，`02-YoBot资产清单.md` §四那 10 个页面的重构量需要先做技术验证。

### D2. 前端技术栈：保留 Vue 3 还是迁 React + Next？

| 选项 | 代价 | 收益 |
|---|---|---|
| **A. 保留 Vue 3，只统一设计语言** | 需自建 token 层与无头组件适配；无法直接复用 Today 的 React 组件思路 | 改动最小；现有 10 页与 37 组件可渐进迁移 |
| **B. 迁移 React + Next.js** | 前端几乎全量重写；构建发布链路重做（静态 SPA → Next standalone） | 可最大程度复刻 Today 的工程范式 |
| **C. 双轨** | 两套设计系统同步成本，长期是技术债 | 过渡期风险最低 |

**建议**：**先做不依赖该决策的事** —— 把 token 层独立出来（纯 CSS 变量，Vue / React 都能消费）。这一步无论选 A 还是 B 都必须做，且能立刻验证「统一设计语言」长什么样。
**判据**：如果「设计统一」是硬要求，**A 的天花板比预期低**（Element Plus 的固定外观会持续与自研语言打架）；但 B 的代价常被低估（不只是重写页面）。

### D3. 「场景配置」做到什么粒度？

| 选项 | 说明 |
|---|---|
| **A. 先只做两种** | 商品销售（现有）+ 个人事务（数字分身默认）。验证配置抽象是否成立 |
| **B. 五种全做** | 按 `03` §1.1 那张表全量实现 |
| **C. 先不做配置** | 硬编码一种通用场景，等产品验证后再抽象 |

**建议：A。** 用两种场景验证抽象是否成立，比一次做五种再发现抽象错了要便宜得多。

### D4. 数据通道的依赖策略（合规相关）

用户已定：**暂未定，先验证**。因此：

- 数据层**设计成可替换的适配器接口**，上游是 MCP 网关还是未来官方通道，接口不变
- **隔离对 `recovery-mcp.js`（逆向加装组件）的依赖** —— 不把它的实现细节泄漏进业务层
- 首版可以依赖它，但**交付物里不包含逆向组件**

**需要留意**：`微信数据对外接入文档.md` 与 `数字分身_Agent开发说明_v1.md` 两份文档含本机路径、端口、进程名，**仓库不能设为公开**。

### D5. YoBot 引擎的改动边界

前面已经确定「复用 `agent/` / `memory/` / `scheduler/` / `channels/`」，但有个前置问题没答：

**YoBot 的原始开发仓库还在吗？**

| 情况 | 逆向材料的定位 | 计划形态 |
|---|---|---|
| **原始仓库在** | 降级为「行为规范 / 参考实现」 | 基于真实工程做增量演进 |
| **原始仓库不在** | 升格为「唯一代码基线」 | 计划必须含「重建可维护工程」主线 |

**从材料看，答案是「不在」**（`02` §五：原始开发仓库未恢复）。所以本方案默认按「以逆向产物为基线」设计。
**但这仍然是整个计划里信息量最大的一次澄清 —— 建议直接确认。**

### D6. 数字分身的交付形态

YoBot 有**完整的插件系统**（`electron/` 53 个模块含安装/清单解析/生命周期/运行时恢复）。数字分身有两种落地形态：

| 选项 | 说明 | 代价 |
|---|---|---|
| **A. 独立页面路由** | 在现有前端里新增六个路由 | 与 D1 的冲突未解时会加剧导航混乱 |
| **B. Electron 插件** | 数字分身作为插件安装，与主线解耦 | 需要先验证插件系统的实际可用性（逆向产物未运行验证过） |

**建议**：**先 A**。插件路径虽优雅，但建立在一个未运行验证过的系统之上；先用路由跑通产品闭环，验证有价值后再考虑插件化。

### D7. 采集覆盖率能不能撑住「记忆类产品」？

这不是技术决策，是**产品定位决策**，但它是数字分身最大的风险（`01` §七）。

**建议**：在 P0 阶段同步做「采集覆盖率实测」—— 连续运行若干天，统计「微信里实际发生的会话」与「落盘到的会话」的比值。
**这个数字决定数字分身的定位**：是「可靠的记忆」，还是「某些场景下的辅助」。**在拿到这个数字之前，任何关于产品定位的承诺都是空的。**

## 五、分阶段路线图

设计原则：**每一步都有可独立验证的产出**，不出现「改造三个月后才能看到效果」。

### P0｜数据打通（当前阻塞点）

| | |
|---|---|
| **目标** | 让 YoBot 产出至少一条真实、可溯源的消息 |
| **交付** | `capability_report.local.json`、`field_mapping.md`、采集链路诊断报告（三个断点各自结论） |
| **验收** | `01` §五的 P0 通过标准全部打勾；写工具调用次数为 0；未读 `protected/` |

**并行可做**（不依赖数据）：事项/知识与技能/分身 Wiki 三页的人工闭环（`03` §三那张表）。

## 六、整体判断（供参考，不替你决策）

1. **数字分身是一次业务层重构，不是功能叠加。** YoBot 的业务层写死成销售场景，数字分身要的正是这层通用化。这条决定了工程性质与工作量预期。

2. **最大的风险不在代码，在数据。** 不是「没有数据源」，是「采集只通了一半」：能读消息，但不落盘；通讯录同步因微信 AX 结构变化而失效。**P0 是唯一正确的起点**，而它的结论可能是「聊天未就绪」——那也是合格产出。

3. **不要重写引擎。** `agent/` 145 模块、`memory/` 14 模块（含用 45 组真实样本校准过的召回阈值）、`knowledge/`、`scheduler/`、`channels/` 都可直接用。**预算应该花在数据打通、业务层重构与前端上。**

4. **最该抄 Today 的三条**：① 任务一等公民（含 `pending_user_answer` 与 `partial/degraded` 结果态）；② 引用式上下文（指针不塞文档）；③ **主动动作的 timing 反馈**（把「打扰」当成可优化的错误类型）。

5. **最该保留 YoBot 的两条**：渠道能力（微信 / iLink / 飞书 / WS）与专家系统 + 灰度发布。

6. **记忆层是互补而非冲突**：YoBot 检索强（召回 + 判决 + 闸门 + 预算），Today 资产化强（可版本化文件 + 可浏览）。**九维 Wiki 需要两者都** —— 这是本次结合里最实的一处技术互补。

7. **唯一能立刻开始、不依赖任何大决策的工作**：把 `product_plan.md` §10.3 的尺寸表 + 原型的实际 CSS 值抽成 **CSS 变量 token 层**。无论 Vue 还是 React、无论哪个决策怎么定，这一步都要做。

8. **两个必须正面回答的前置问题**：
   - **YoBot 的原始开发仓库还在吗？**（决定 D5）
   - **采集覆盖率实测是多少？**（决定 D7，也决定产品的定位能说多满）

## 七、这份判断里我不确定的地方

| 不确定项 | 为什么不确定 | 怎么消除 |
|---|---|---|
| `chat_history` 不落盘的**真实原因** | 只确认了「目录不存在」，三个候选原因未逐一排除 | P0 阶段实测 |
| 通讯录同步的 AX 失效**能否在不改 RPA 的前提下修复** | 需要看 Python 层实现，而 Python 层**只有反汇编**（`02` §五） | P0 阶段评估，或接受「需重写该模块」 |
| YoBot 引擎模块的**实际可运行性** | 全部来自静态逆向，**从未真实启动运行过** | 需要真实运行验证；不能只靠这份清单 |
| 插件系统的**可用性** | 同上，且影响 D6 | P2 之后评估 |
| 「场景配置」抽象是否成立 | 只有两种场景时才敢下结论（所以建议 D3 选 A） | P2 阶段用真实数据验证 |
