# 差异地图与待决策项

> 这份文档的作用：**在 GPT 出计划之前，先把「哪些必须由人拍板」摊开**。
> 计划的质量上限取决于这些决策的清晰度——不决策，GPT 只会给你一份所有选项都提一遍的和稀泥方案。

---

## 一、逐层差异地图

图例：**保留** = YoBot 现有实现直接留用 ｜ **改造** = 有基础但需重塑 ｜ **新建** = 两边都没有

| 层 | YoBot 现状 | Today 做法 | 判定 | 说明 |
|---|---|---|---|---|
| **设计 token** | Element Plus 主题 + 自定义 CSS | 自研 `opal-tokens`（Tailwind v4 CSS 变量） | **新建** | 设计统一的唯一真正抓手。不建 token 层，「统一」只是把组件抄一遍 |
| **基础组件库** | Element Plus | Radix / Base UI 无头组件 + CVA | **改造** | Element Plus 是「外观固定」的成品组件，与自定义设计语言冲突；建议转无头组件方案 |
| **业务组件** | 37 个 `.vue` | 卡片 + Widget 运行时 | **改造** | 业务逻辑可留，表现层重做 |
| **页面结构** | 10 个多页路由 | 单时间线 + 卡片 + 任务面板 | **改造** | 见第三节逐页方案 |
| **前端技术栈** | Vue 3 + Vite + Pinia | React + Next.js | **决策** | 见 D1 |
| **前后端契约** | 裸 HTTP（97 端点）+ WebSocket | 生成式契约 + 能力协商（147 条 IPC） | **改造** | 高价值、可渐进。见 D2 |
| **实时事件模型** | `websocket.js` + `channels/` | `realtime-contract` 三分命名空间 | **改造** | YoBot 已有渠道抽象，缺任务事件模型 |
| **Agent 编排** | `agent/agentic/` 已有会话编排、幂等、投递账本 | 任务为一等公民 + 步骤 DAG | **改造** | YoBot 有基础，需补任务状态机与中间态（`pending_user_answer`） |
| **上下文管理** | `context/pruner.js` | 四道结构性隔离 | **改造** | 已有裁剪器，需补「引用式回复」与消息分层可见性 |
| **记忆** | 向量召回 + LLM 判决 + 注入闸门 + 配额（**检索式**） | Markdown VFS + 凌晨 reflect + 三档注入（**资产式**） | **融合** | **互补而非替代**：保留 YoBot 的检索能力，增加 Today 的资产化与可视化 |
| **知识库** | `knowledge/` 有配额、容量核算、原件保留（`raw/` + `doc.md`） | — | **保留** | YoBot 这块比 Today 资料更完整 |
| **技能体系** | `skills/` 72 模块 + MCP 客户端与服务端 + 用户可安装目录 | Widget 生态 + GUI Agent 工具集 | **保留并扩展** | YoBot 已有生态雏形 |
| **专家系统** | `agent/expert/` 能力组合 + 灰度发布 + 路由守卫 | — | **保留** | 这是 YoBot 的差异化资产，Today 材料里没有对应物 |
| **调度** | `scheduler/`（执行预设 / 变更意图 / 结果模型） | automation + cron + 六形态主动动作 | **改造** | 机制在，缺产品化的主动动作形态 |
| **主动动作** | 无明确对应 | 六形态 + 三维反馈（含 timing） | **新建** | 这是 Today 最值得抄的一块 |
| **渠道** | 微信 RPA / 微信 iLink / 飞书 / WS | — | **保留** | **YoBot 的核心护城河** |
| **本地 GUI 自动化** | 微信专用 RPA（垂直） | 通用 GUI Agent（106 工具 + 配方学习） | **决策** | 见 D5 |
| **多品牌白标** | 运行时品牌配置（`channel_id`） | 编译期区域构建（global / cn） | **保留并升级** | 可融合：运行时白标 + 编译期差异化能力 |
| **商业化** | 本地 License（机器码 / 激活 / 解绑） | 云端账号 + 订阅 | **决策** | 见 D4 |
| **质量工程** | 有少量测试（`tests/`） | Storybook + Playwright 视觉回归 + E2E + MSW | **新建** | 不做这块，前端统一无法长期维持 |
| **i18n** | 白标多品牌隐含需求 | `i18next` + 键值一致性校验脚本 | **新建** | 白标必然要多语言 |

## 二、必须先拍板的决策点

### D1. 前端技术栈：保留 Vue 还是迁到 React + Next？

| 选项 | 代价 | 收益 |
|---|---|---|
| **A. 保留 Vue 3，只统一设计语言** | 需要自己实现 token 层与无头组件适配；无法直接复用 Today 的 React 组件思路 | 改动最小，现有 10 个页面与 37 个组件可渐进迁移；团队技能不重建 |
| **B. 迁移到 React + Next.js** | 前端几乎全量重写；构建与发布链路重做（静态 SPA → Next standalone）；需要处理 Electron 内嵌服务的加固 | 可最大程度复刻 Today 的产品形态与工程范式；生态与人才供给更宽 |
| **C. 双轨：新功能用 React，旧页面留 Vue** | 两套设计系统的同步成本，长期是技术债 | 过渡期风险最低 |

**我的倾向**：如果「前端设计完全统一」是硬要求，**A 的天花板比你想的低**——Element Plus 的组件外观与自研设计语言会持续打架。但如果团队是 Vue 背景，**B 的代价被严重低估**（不只是重写页面，还包括 Next 内嵌服务、SSR/CSR 边界、Electron 安全加固）。
**建议**：先做一件不依赖该决策的事——**把 token 层独立出来**（纯 CSS 变量，Vue / React 都能消费）。这一步无论选 A 还是 B 都必须做，且能立刻验证「统一设计语言」到底长什么样。

### D2. 「设计统一」统一到哪一层？

三档，代价递增：

1. **视觉语言统一**：token 层 + 组件规范文档（设计稿层面统一）
2. **组件库统一**：一套组件代码，两端复用（需要同技术栈）
3. **工程范式统一**：契约生成、质量工程、i18n、测试体系全部拉齐

**建议**：**1 是必做项**，**3 是真正的长期收益**（契约 + 测试体系），**2 反而最不紧急**——组件代码的价值远低于规范和 token。

### D3. Agent 内核：保留 YoBot 内核还是重写？

这是个真问题，必须正面回答：

- YoBot 内核（约 380 个模块）**已实现**：会话编排、上下文裁剪、记忆三件套（召回/判决/注入）、知识库配额、专家能力灰度、MCP 双端、技能目录、调度器、会话配额、分布式追踪上传
- **但它是逆向产物，不是可维护的开发仓库**：无原始 TypeScript 类型、无构建配置、无完整测试

| 选项 | 说明 |
|---|---|
| **保留并演进** | 直接把 `recovered/app/dist/electron/` 当作代码基线继续改。快，但**类型缺失、注释与实现可能脱节、无法确定编译链路** |
| **按契约重写** | 以现有实现为**行为规范**，重新写一份带类型的干净工程。慢，但可维护 |
| **混合** | 稳定的底层（记忆、知识库、MCP）保留；要深度改造的层（编排、任务模型、上下文隔离）重写 |

**建议**：混合。**判据是「这一层要不要大改」**——要重写模型的部分顺手重写代码；能原样复用的部分不要为了洁癖重写。
⚠️ **这个决策必须先确认一件事**：YoBot 的**原始源码是否还在**（是否有私有的开发仓库）。如果原始工程存在，整份逆向材料的定位就从「代码基线」降级为「行为规范」，方案会完全不同。**这是整个计划里最关键的前置问题。**

### D4. 云端能力要不要？

| | YoBot（本地） | Today（云端） |
|---|---|---|
| 账号 | 本地 License + 机器码 | 云端账号（Auth0 / better-auth） |
| 编排 | 本地 Agent | 云端 Agent 编排 → 本地执行 → 结果回传 |
| 数据 | 本地文件 + 向量库 | 云端同步 + 本地缓存 |

**本地优先是 YoBot 的合规优势**（微信数据不出本机）与**成本优势**，但限制跨设备与团队协作。
**建议**：保留本地执行为主，云端只做**账号、授权、模型网关、Trace 上传**这类无用户数据的功能。**不要把微信对话数据上云** —— 这既是合规底线，也是产品卖点。

### D5. 微信 RPA 的定位（风险最高的一项）

必须正视三件事：
1. 基于 Accessibility / ScreenCaptureKit / CGEvent 的界面自动化控制微信，**违反微信用户协议**，存在账号封禁风险
2. 风控在持续升级，**这是一个对抗性赛道**，投入产出比会逐年恶化
3. `standalone/scripts/` 里的授权绕过脚本**不得进入产品分发**

**三条可选路线**：

| 路线 | 说明 | 风险 |
|---|---|---|
| **维持 RPA 为主** | 现状延续，能力最强 | 合规与封禁风险持续 |
| **RPA + 合规通道双轨** | RPA 用于**辅助人工**（草稿、建议、提醒），实际发送走企业微信 / 官方开放接口 | 能力受限，但可持续 |
| **抽象成通用 GUI Agent** | 把微信 RPA 降级为一个专用配方，底座通用化 | 技术风险高，见 D6 |

**建议**：**明确区分「代替用户发送」与「辅助用户决策」**。后者在合规上安全得多，且 Today 的产品形态（主动建议 + 卡片 + 用户确认）天然适配。**这是我认为最值得重新定位的一点。**

### D6. 要不要做通用 GUI Agent？

Today 的 `ghost*` 29 个工具（截图 → 解析 → 定位 → 操作 → 学成配方回放）很诱人，但：
- 通用 GUI Agent 在真实场景的失败率**远高于**垂直专用实现
- 需要大量真实场景数据做回归
- 权限管理（辅助功能 / 屏幕录制 / 输入监控）是持续的运维负担

**建议**：**先不做通用化，先做「配方录制回放」**——即只保留「把人工操作学成配方再重放」这一条，跳过「模型理解屏幕自主决策」。前者可控，后者是不可控的承诺。

### D7. 多品牌白标保留吗？

必须保留（可能是主要收入来源）。但要升级：
- **运行时**：品牌配置（现有能力，继续用）
- **编译期**：能力差异化构建（按渠道裁剪功能，参考 Today 的 `FEATURE_ENABLE_X` + `REGION` 模式）
- **约束**：统一设计系统**不得破坏换肤能力** —— 所有颜色必须走 token，不能组件内硬编码

## 四、给 GPT 的三个前置问题（建议先回答）

在让 GPT 出计划之前，先自己回答这三条。它们直接决定计划的形态：

1. **YoBot 的原始开发仓库还在吗？** 如果不在，整个方案要按「以逆向产物为唯一基线」来设计，D3 的答案会偏向重写。
2. **「统一」的目标是内部工程效率，还是对外产品观感？** 如果是后者，优先级是 token + 视觉规范 + 关键页面；如果是前者，优先级是契约层 + 质量工程。
3. **微信 RPA 在商业上还能做多久？** 这决定你要不要把资源投在「把它做得更强」还是「把它换掉/降级」。

## 五、我的整体判断（供参考，不替你决策）

1. **不要在 YoBot 上「改造」出 Today，而是抽出一个新外壳复用 YoBot 引擎。** 因为前端与内核本来就是解耦的（静态 SPA + 独立服务子进程），换壳的成本远低于把 Vue 应用逐页改造成单时间线。
2. **先做三件不依赖任何大决策的事**：① 抽出设计 token 层；② 补齐质量工程（视觉回归 + E2E）；③ 把前端 ↔ 引擎的契约生成化。这三件在任何路线下都要做。
3. **最大的认知纠偏**：YoBot 缺的不是 AI 能力，是**产品形态**。它的引擎比前端成熟得多——所以别把预算花在重写引擎上。
4. **最该抄 Today 的两条**：**任务作为一等公民**、**主动动作的三维反馈（尤其 timing）**。
5. **最该保留 YoBot 的两条**：**渠道能力**（微信/飞书/iLink）与**专家系统 + 灰度发布**。
