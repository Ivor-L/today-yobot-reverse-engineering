# PLANNING — 让 GPT 产出 YoBot → Today 式改造计划

这个目录是**给 AI 助手的输入包**。它不做计划，它让计划能做得好。

---

## 先回答一个前置问题

**YoBot 的原始开发仓库还在吗？**

这个问题决定一切：

| 情况 | 逆向材料的定位 | 计划形态 |
|---|---|---|
| **原始仓库在** | 降级为「行为规范 / 参考实现」 | 计划基于真实工程做增量演进，逆向材料只用于对照 |
| **原始仓库不在** | 升格为「唯一代码基线」 | 计划必须包含「重建可维护工程」这条主线 |

**如果这个问题没答案，GPT 给出的计划一定是模糊的。** 这是整个流程里信息量最大的一次澄清。

---

## 三步流程

### 第 1 步：摊开决策（约 15 分钟，自己做完）

读 `03-差异地图与待决策项.md`，把 **D1–D7 七个决策点**过一遍。

**不必现在全部决定**，但要能回答「我倾向哪个」和「哪个我还不知道」。GPT 拿到这个倾向，输出的才是有立场的方案，而不是七个选项各写一遍。

其中 D3（内核保留还是重写）依赖上面那个前置问题的答案。

### 第 2 步：把提示词扔给 GPT

打开 `00-给GPT的提示词.md`，复制 `---` 之间的全部内容。

- **GPT 能访问本仓库** → 直接粘贴，它会自己核对文件
- **GPT 不能访问** → 粘贴提示词 + 上传 `01` / `02` / `03` 三份文档作为附件

**技术选型建议**：用推理模型（o 系列 / GPT-5 thinking / Claude with extended thinking），开新对话。这类任务最怕上下文里混入无关历史。

**不要一次问完**。第一轮拿到的应该是一份**带决策点的粗计划**，然后按提示词末尾的「追问模板」逐层往下钻。追问比重新提问有效得多。

### 第 3 步：用事实底稿做交叉验证

GPT 会不可避免地产生幻觉，尤其是涉及 YoBot 具体实现时。**用 `01-YoBot现状-事实清单.md` 当验伪工具**：

| 如果 GPT 说 | 去核对 |
|---|---|
| 「YoBot 目前没有记忆系统」 | 错。`recovered/app/dist/electron/memory/` 有 14 个模块 |
| 「需要新建知识库能力」 | 错。`knowledge/` 已有配额与容量核算 |
| 「YoBot 没有 MCP 支持」 | 错。`skills/mcp/` 同时有客户端与服务端 |
| 「前端和内核耦合，要先解耦」 | 错。静态 SPA + 独立服务子进程，本来就是解的 |
| 「微信 RPA 是 YoBot 唯一的 AI 能力」 | 错。`agent/` 145 个模块 + `agent/expert/` 专家系统 |
| 提到任何「YoBot 已经在做 X」 | 要求它给出证据路径，然后去仓库核对 |

**判据**：凡是没有标证据路径的 YoBot 现状描述，一律当「未验证」处理。

## 两个提醒

**一、反向验证比正向提问更重要。** 你手里有一份带证据路径的事实清单，这是绝大多数人做这类规划时没有的优势。别浪费它——GPT 的每一条关于现状的断言，都值得花 30 秒核对。

**二、这份材料是逆向产物，本身就有边界。** 它证明的是「代码里有什么」，不是「功能实际能跑成什么样」。恢复的代码从未真实启动过。任何涉及「YoBot 现在能做什么」的商业判断，都必须用真实运行验证来补，不能只靠这份清单。

最后一页判断写在 `03` 的第五节——**YoBot 缺的不是 AI 能力，是产品形态；别把预算花在重写引擎上。** 你可以不同意，但请让 GPT 正面回应这个判断，而不是绕过去。
